## Analyze

- **Storage:** 16 of the 19 literals are not stored exactly; the error is at most half an ulp but has
  either sign (0.1 is stored high, 0.3 low), which is why `0.1 + 0.2` lands one ulp above the
  double for 0.3.
- **Multiplying by 100** to get cents is where money breaks: none of the four `* 100` rows
  is a whole number; three land just below one (1.15, 4.35, 19.99), so truncation (`(long)`,
  `int()`, `Math.trunc`) gives a cent less, and rounding to cents after the fact is wrong for 1.005 (`Math.round(1.005 * 100) / 100`
  is 1 in Node.js 24, checked on this machine).
- **Large integers:** above 2^53 a double cannot hold every integer, so adding 1 is lost; the Money
  results stay exact.
- **Sums:** naive error grows roughly with n (1e-16 at n = 10, 1e-6 at n = 1,000,000 for 0.1) and
  changes sign along the way; Kahan summation removes it for these inputs. Even the worst naive
  error here is far below a cent: the money bugs come from conversions and comparisons, not from
  drift alone.
- **Money API:** every shared case agrees in all three languages, including the overflow edge at
  ±92,233,720,368,547,758.07 USD and the refusals of `12.345 USD`, `1e3`, `.5`, `1,000.00` and
  Arabic-Indic digits (which Python's `int()` would accept).

## Improve

- Two defects found while building, both in the test code: on Windows `PrintStream.println`
  writes `\r\n`, so the Java CLI test normalises line endings; a JS invariant compared `0` with
  `-0` strictly and now checks that `compare(a, b) + compare(b, a)` is 0.
- The `explain` output label for the representation error is `stored-input`.

## Reproduce

`currencies.tsv` are hand-written. Random tests use fixed seeds (20261114). No models or downloads
are involved.
